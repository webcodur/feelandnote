# 경로 잇기 (Travel) — 발주서

> **최종 실측 체크: 26.07.31** — 당시 실 DB 전량 대조: 현재 `celeb_contents`로 이관된 관계 11,331행·인물 1,476명·태그 864건으로 그래프 구축, 200회 스트레스 시험, 전송량(gzip 489KB) 실측. selectInChunks 교정 전후 비교.

---

## 무엇을 하는 게임인가

두 인물이 화면에 뜬다. 출발 인물에서 시작해, "같은 책을 서재에 둔 인물" 또는 "같은 세력에 속한 인물"을 한 명씩 밟으며 도착 인물까지 이동한다. 정해진 이동 횟수(예산) 안에 도착하면 성공이다.

최단 경로를 찾는 게임이 아니다. **도달 자체가 목표이고, 예산 초과분만 감점된다.** 이동할 때마다 "왜 이어졌는지"(공유한 작품 제목 또는 세력 이름)를 보여주므로, 인물 간 뜻밖의 연결을 발견하는 재미가 핵심이다.

## 기존 게임과의 축 차이

| 게임 | 핵심 축 | 경로 잇기와의 차이 |
|------|---------|-------------------|
| 교차 격자 (grid) | 조건 교차 + 기억 인출 | 셀 하나에 한 명을 떠올림. 관계 그래프 없음 |
| 넷씩 넷 (groups) | 범주 분류 | 16명을 묶음으로 나눔. 경로 탐색 아님 |
| 근접도 (proximity) | 벡터 거리 | 단일 정답에 온도로 접근. 그래프 이동 아님 |
| **경로 잇기 (travel)** | **관계 그래프 탐색** | 인물 간 실제 연결(콘텐츠·세력)을 밟아 이동. 유일하게 "경로"가 존재 |

## 허브 붕괴 위험과 해소 논증

### 문제

선행 검토가 지적한 위험: "인기 콘텐츠(성경·논어)와 대형 태그(14명+)가 허브가 되면 거의 모든 쌍이 2단계 이내에 이어져 퍼즐이 붕괴한다."

### Travle식 해법이 이 위험을 해소하는 이유

1. **목표를 "최단 경로 찾기"에서 "예산 내 도달"로 바꿨다.** 모든 쌍이 2단계라도, 예산을 3으로 주면 퍼즐이 아닌 것이 맞다. 하지만 출제를 "최적 경로 3~6단계인 쌍"으로 제한하므로 2단계 쌍은 애초에 출제되지 않는다.

2. **허브 캡을 도입했다.** 서버 조회 단계에서:
   - 태그 인원 > 20명인 태그는 간선을 생성하지 않는다.
   - 콘텐츠 공유 인원 > 10명인 콘텐츠는 간선을 생성하지 않는다.
   이로써 "모든 경로가 성경 한 권을 거쳐 2단계"인 상황을 원천 차단한다.

3. **재미의 축이 다르다.** 최단 경로 게임에서는 "이미 2단계라서 시시함"이 치명적이지만, Travle식에서는 "예산이 넉넉해서 도착은 쉬운데 어떤 경로를 밟을지 고르는 재미"가 핵심이다. 경로마다 다른 연결 이유(책 제목·세력 이름)가 뜨므로, 쉬워도 흥미로운 발견이 생긴다.

4. **체험 표본 실측으로 확인됐다.** 50명 피트 그래프에서 100쌍 샘플링 결과:
   - 연결 가능: 100% (고립 노드 0)
   - 경로 3~6 비율: 66%
   - 8회 출제 모두 성공 (최적 5~6단계)

## 한 판 완주 흐름

1. **로비** — 규칙 안내 카드 3종, 시작 버튼.
2. **게임 시작** — 출발·도착 인물이 상단에 표시된다. 이동 예산(최적+3)이 진행 바에 보인다.
3. **이웃 선택** — 현재 인물의 이웃 목록이 카드로 뜬다. 각 카드에 "왜 이어졌는지"(📖 공유 콘텐츠 / 🏷️ 같은 세력)가 함께 표시된다. 도착 인물이 이웃에 있으면 금색 강조.
4. **이동** — 카드를 누르면 한 칸 전진. 경로 이력이 위에 쌓인다.
5. **도착** — 도착 인물에 닿으면 예산 내/초과에 따라 결과 분기.
6. **포기** — 아무 때나 포기 가능.
7. **결과** — 점수, 내 경로, 최적 경로(BFS)를 나란히 보여준다. 다시 하기/로비 버튼.

| 항목 | 값 |
|------|-----|
| 출제 쌍 제한 | BFS 최적 경로 3~6단계인 쌍만 출제 |

| 이웃 표시 상한 | 20명 (검색으로 필터 가능) |

## 조회 설계

- **패턴**: 전수 조회 → 단일 키 7일 공유 캐시 → 클라이언트에서 BFS.
- **선례**: `all-persona-vectors`(유사 인물 추천)가 같은 구조.
- **캐시 키**: `"travel-game-graph"`, tags: `[CONTENTS, CELEBS, TAGS]`
- **페이징**: `selectAllPages` + `.order('id', { ascending: true })`
- **허브 캡**: 태그 20명 초과 제외, 콘텐츠 10명 초과 제외.
- **전송량 추정**: 50명 피트에서 간선 ~140개. 실 서비스 1,692명에서는 허브 캡 후 추정 50,000~100,000 간선 × ~80B = 4~8MB raw → gzip ~400KB~1MB. 7일 1회 조회이므로 egress 영향 미미.

## 간선 확장 실측 결과 (26.07.31)

### 원인 진단

당시 `user_contents`(현 `celeb_contents`) 조회에서 `.in("user_id", [...profileMap.keys()].slice(0, 200))` — **첫 200명분만** 조회하고 있었다. PostgREST `in()` URL 한도(462건에서 실패한 실측 이력)를 의식해 `.slice(0, 200)`을 넣었으나, `selectInChunks`를 사용하지 않아 나머지 1,276명의 콘텐츠 기록이 통째로 누락됐다. 현재 쿼리는 `celeb_contents.celeb_id`를 쓴다.

추가로 `content_locales` 제목 조회에서도 `.limit(chunkSize)`이 걸려 있어 chunk당 200건을 초과하는 결과를 잘랐다.

### 교정 내용

1. **`celeb_contents` 조회**: `selectInChunks(celebIds, chunk => selectAllPages(...))`로 교체. 1,476명 ID를 200개 단위로 나눠, 각 chunk 안에서도 PostgREST 1,000행 상한을 페이징으로 우회한다.
2. **`content_locales` 제목 조회**: `selectInChunks(contentIds, chunk => ...)`로 교체. `.limit()` 제거.
3. **허브 캡**: 변경 없음 (태그 20명, 콘텐츠 10명). 실측으로 적정성 확인.

7일 단일 키 공유 캐시이므로 월간 egress ≈ 489KB × 4회 = ~2 MB. Pro 250GB 기준 0.0008% — 무시할 수 있다.

### 남은 275명 고립의 정체

고립 275명은 **아무 세력에도 소속되지 않고 콘텐츠도 2명 이상 공유하지 않는** 인물이다. 게임은 연결된 1,201명 풀에서만 출제하므로 플레이에 영향 없다. 향후 인물 간 연결이 추가되면 자동으로 게임 풀에 합류한다.
