# Kiro에서 GPT 호출

이 프로젝트의 Kiro 모델 선호순위는 **GPT-5.6 Sol > Claude Opus**다. 비용 절감 기준이 아니라 결과 품질 기준이다. 별도 이유가 없으면 `--model gpt-5.6-sol --effort high --agent-engine v3`를 쓴다.

## 병렬 구조

기본 구조는 **`[Kiro 터미널(코디네이터) → 내부 조사 워커 최대 3대] × n`**이다.

- 각 터미널 프롬프트에 `이 터미널의 내부 에이전트/워커 총량은 3대를 넘기지 않는다`고 직접 쓴다.
- 코디네이터는 정확한 키 배정·충돌 감시·결과 확인만 하고 별도 조사 레인을 맡지 않는다.
- 내부 워커의 재귀 위임과 완료 건 재시도를 금지한다.
- 상위 오케스트레이터가 서로 겹치지 않는 정확한 키를 터미널별로 나눈다. 한 워커가 한 키의 조사·판정·원자 저장·자체검증을 끝낸다.
- 전역 `n`은 Kiro 계정의 공유 호출량에 따라 달라진다. 현재 무인 기본값은 `scripts/kiro-call.mjs`의 `DEFAULT_TOP_LEVEL_CONCURRENCY`를 따른다.

실측상 배경 Kiro 3대와 함께 돌린 `3터미널 × 내부 3워커`는 9/9 파일을 만들었지만 한 터미널이 후처리 중 `ClientThrottleError`를 냈다. `2터미널 × 내부 3워커`는 실행 중 배경 Kiro가 3대로 늘어난 조건에서도 6/6 결과와 전체 감사를 오류 없이 끝냈다. 따라서 3×3을 무인 기본값으로 올리지 않는다.

## 호출과 종료

직접 spawn을 다시 만들지 말고 `scripts/kiro-call.mjs`의 `runKiro()`를 import한다. 이 헬퍼는 실제 `kiro-cli.exe`를 찾아 V3·Sol·비대화 플래그를 붙이고, 자기가 띄운 프로세스 트리만 종료한다.

Kiro 루트 프로세스가 끝나도 보조 프로세스가 stdout 핸들을 오래 쥐어 Node의 `close` 이벤트가 늦어질 수 있다. 완료 감시는 `exit`를 기준으로 하고, 작업 완료는 다음 세 가지로 판정한다.

1. 배정된 정확한 결과 파일이 모두 존재한다.
2. 각 파일을 다시 파싱하고 키·스키마를 검사한다.
3. 도메인의 결정론적 전체 감사를 통과한다.

코디네이터의 자연어 완료 보고만으로 다음 배치나 DB 반영으로 넘어가지 않는다.

## 제한 대응

`ClientThrottleError`, `USER_REQUEST_RATE_EXCEEDED`, `Too many requests`를 강한 제한 신호로 본다.

- 이미 결과가 생긴 키는 다시 조사하지 않는다.
- 미완료 키만 새 묶음으로 만들고 전역 터미널 수 `n`을 한 단계 낮춘다.
- 다른 Kiro 배치가 3대씩 계속 재기동될 수 있으므로 시작 순간만 보지 말고 실행 중 제한 신호도 감시한다.
- 제한과 무관한 개별 실패는 해당 키만 격리한다. 전체 묶음을 처음부터 되돌리지 않는다.

긴 프롬프트에는 작업 루트, 읽을 룰북, 정확한 키, 허용된 쓰기 경로, 기계 검증 명령, 재귀 위임 금지를 넣는다. 웹 조사는 프로젝트 규칙대로 후보 URL 검색과 본문 열기를 구분하고, 본문은 먼저 `insane-search`를 사용한다.
