### 처리 체계 — 레인 릴레이

배치 라운드에서 레인 릴레이로 바꿨다. 메인이 관문 사이마다 개입하던 구조를 걷어내고, **레인 7개(a~g)가
각자 명단을 들고 조사 → 선별 검증 → 문장 검사 → 5건마다 반영을 독립적으로 순환한다.** 레인은 다른
레인을 기다리지 않는다.

- 규약은 `lanes/00-레인규약.md` 하나다. 레인별 명단은 `lanes/todo-<레인>.md`(건마다 [안내]·
  [현재 탐구]·[감사 지적]을 실어 둔다), 산출은 `lanes/result-<레인>.md`다.
- `lanes/build-lane.py <레인> [slug ...]`가 result 파일을 파싱해 `apply-<레인>.json`을 만들고
  `apply-relay.ts`가 반영한다. **교정은 result 파일 본문을 직접 고쳐 다시 태운다.**
- **한 건 끝날 때마다 즉시 append하고 5건마다 반영한다.** 몰아 쓰면 한도 소진 시 전량 날아간다.
- 앞선 두 갈래는 끝났다. **선별**은 발주 전에 현행 원문을 집 기준(사실 구체·한 줄기·사실로 끝남·
  220~500자·안내 재탕 아님)으로 갈라 승인·교정 약 190건을 조사 없이 `ai_reviewed`로 복귀시켰고
  (판정 근거는 `s*-apply.ts` 주석에 배치별로 남아 있다), **문장 교정**은 e1~e13 배치 98건을
  처리했다(그대로 승인 33, 교정 65). 교정으로 못 고치는 것(220자 미달, 새 사실 필요, 주객전도,
  문헌 비교형)은 재작성으로 격상했다.
- 서브에이전트는 `model`을 지정하지 않으면 세션 모델을 물려받는다. Fable 5 세션에서 한도가 차면
  조사·검증 에이전트가 동시에 죽으므로, 레인을 크게 돌릴 때는 세션 모델과 잔여 한도를 먼저 본다.
  건별 즉시 append 지침 덕에 사망해도 생존분은 회수되니, 재발주는 잔여분만 한다.

  '앤더블')는 기반영된 han-yu-jin·kim-gyu-vin과 어긋나면 그쪽도 함께 고친다.

### 세 관문 파이프라인 — 이 큐를 처리하는 방식

한 배치 8건을 **조사 → 사실 검증 → 문장 검사 → 반영** 순으로 통과시킨다. 각 관문은 별도
서브에이전트가 맡고, 메인은 관문 사이에서 판단만 한다. 서브에이전트가 검색 결과를 자기
맥락에서 태우고 표만 돌려주므로 메인 맥락이 배치 수에 비례해 늘지 않는다.

- **조사** — 4건씩 두 조. 발주 프롬프트는 `rework-fetch`가 `rework-rules.txt`를 머리에 붙여
  자동 생성한다. 여기에 건별 단서(어느 원전 몇 장, 어느 사건)를 손으로 덧붙인다. 이 단서가
  결과 품질을 가장 크게 좌우한다.
- **사실 검증** — 조사 결과의 `핵심사실` 줄에 실린 인용을 원전과 대조한다. 판정은
  확인·불일치·미확인·단일출처 넷. **미확인은 대목을 들어내고, 단일출처는 출처를 본문에
  밝혀 살린다.** 둘을 섞으면 조치를 정할 수 없다.
- **문장 검사** — 사실은 건드리지 않고 문장 구조만 본다. **분량을 늘리지 말라는 제약을
  같이 준다.** 쉼표를 마침표로 바꿔 끊는 수가 글자 수 변동 없이 가장 잘 듣는다.
  손댈 데 없으면 SKIP. 실제로 절반 가까이가 SKIP으로 나오며 그것이 정상이다.

**조사는 agy가 아니라 클로드 서브에이전트로 돌린다.** agy(제미니)로 돌린 초기 배치는 반려가
잦았고, 서브에이전트로 바꾼 뒤 배치 전건 통과가 반복해 나왔다. 원전 전문(구텐베르크·위키문헌·
Perseus·FRUS)까지 파고드는 깊이가 다르다.

**파이프라인이 잡아낸 것들.** 발주자가 인물을 잘못 지목한 건(`choi-min-ho`), 인용한 URL에
그 내용이 없던 건(브라흐마·범규), 기사 게재일을 사건일로 쓴 건(브래드 라이트캡), 널리 도는
통설이 원문과 다른 건(도스토옙스키 계약 분량은 "160쪽"이 아니라 인쇄전지 12장).

### 큐가 줄지 않는 유형 — 소재 고갈

안내가 그 인물의 가장 유명한 이야기를 통째로 담고 있으면 탐구에 쓸 것이 남지 않는다.
원전이 두꺼운 신화·중세 인물은 다른 대목을 찾으면 되지만(펜리르는 글레이프니르 이전의
레딩·드로미, 가웨인은 아예 다른 작품인 『가웨인 경과 녹색 기사』), 사료에 한 장면만 남은
인물은 방법이 없다. 그런 건은 재조사불가로 물러서고 사람이 정한다.

## 결함 세 종류와 판정 규칙

1. **탐구가 안내를 의미만 바꿔 되풀이** — 어휘가 겹치지 않으면 기계로 못 잡는다
2. **평판으로 끝나는 공허한 마무리** — 한국어·영어 모두 정규식으로 잡아 관문이 반려한다
3. **무정보 문장** — 사람이 읽어도 판정이 갈린다. 지침의 아리스토텔레스 조항이 판정법을 쥔다

**"고칠 것 없음"은 선택지가 아니다.** B(문장 교정) 아니면 A(조사 재작성)다. A와 B를 가르는 선은
지침 파일에 있으니 발주 프롬프트에 다시 실을 필요가 없다. PASS 경로는 폐기했고 관문이 `update`
외의 action을 반려한다.

한 회차 절차:

1. 스냅샷 재생성 → 묶음 생성기 실행. 원장 미완료 인물을 slug 순 8명 묶음으로 산출한다.
   품질 검사기가 뽑은 재작업 큐를 돌릴 때는 `--slugs=<큐.json>`으로 원장 완료 여부를 건너뛴다
2. 묶음마다 서브에이전트 1개 발주. `relay-instructions.md` 하나만 Read시킨다. 문서를 여럿
   읽히면 묶음당 토큰이 5분의 1 더 든다
3. 발주 프롬프트에 **인물별 이름·직업·생몰년을 함께 적는다.** slug만 주면 동명이인을 잘못 짚는다.
   실제로 '유진'을 아이돌로, 'young-sam-kim'을 김영삼 전 대통령으로 착각한 발주가 나왔다
4. **한 명 끝낼 때마다 즉시 파일로 쓰고 반영 관문에 태운다.** 8명을 모아 마지막에 쓰면 한도
   소진 시 전량 날아간다(14차 웨이브에서 240명 손실)
5. 관문 통과분만 반영, 원장 기록. 반려·충돌은 다음 회차에 자동 재등장

### 재개 시 주의

- 레인은 6개를 넘기지 않는다. 한도로 죽을 때 손실이 레인 수에 비례한다
- 레인이 먼저 끝나 새 묶음을 뽑을 때는 `--busy=<진행 중 폴더>`로 다른 레인이 붙잡은 인물을
  제외한다. 두 레인이 같은 사람을 처리하면 뒤쪽이 조건부 갱신에서 충돌한다
- `review_status` 초기화 같은 일괄 갱신을 하면 `updated_at`이 바뀌어 **기존 스냅샷이 전부
  충돌한다.** 초기화 후에는 스냅샷을 반드시 다시 뽑는다
- 스냅샷이 낡아 튕긴 원고는 버리지 말고 단건 회수기로 살린다
- 회차당 실측: 묶음(8명)당 9~16만 토큰, 소요 7~12분. 6개 레인 동시 발주 기준 회차당 48명
- 보류 판정은 원장에 직접 적어야 남는다. 관문을 타지 않으므로 기록하지 않으면 다음 회차에 같은
  인물이 계속 다시 뽑힌다

## 구조로 남은 두 구멍

릴레이를 한 바퀴 돌리며 드러난 것이고, 다음 회차를 돌리기 전에 정하는 편이 낫다.

1. **관문과 검사기가 서로 다른 규칙을 본다.** `apply-celeb-reading-relay.ts`는 공허한 마무리와
   길이·필드만 반려하고, 탐구가 안내를 되풀이하는 V3와 새 사실 부재 V4는 보지 않는다. 그래서 전량
   통과 뒤 검사기를 돌리자 25명이 새로 걸렸다. 관문이 V3·V4를 함께 보게 하거나, 검사기 실행을
   회차 절차에 못박아야 같은 일이 반복되지 않는다
2. **쓴 쪽이 판정까지 한다.** 지금은 레인 서브에이전트가 자기 원고를 스스로 합격시키고 끝난다.
   기계 검사기는 어휘가 겹치지 않는 되풀이를 못 잡으므로, 다른 세대가 읽고 반려하는 검토 레인이
   없으면 품질은 쓴 사람 수준에 묶인다
   > **탐구 재작업 큐에서는 이 구멍을 메웠다.** 위 「세 관문 파이프라인」이 조사·검증·문장 검사를
   > 서로 다른 에이전트에 나눠 맡긴다. 쓴 쪽은 판정하지 않는다. 전량 릴레이를 다시 돌릴 때도
   > 같은 구조를 쓰는 편이 낫다.
