# 필앤노트 시네마 — 개요와 게시글·예약 정비

## 무엇을 만드는 작업인가

[필앤노트 시네마](https://feelandnote-cinema.tistory.com)는 필앤노트의 영화 감상 기록을
검색으로 발견할 수 있는 글로 만드는 티스토리 채널이다. 본 서비스의 검색 노출이 부진한
상황에서 외부 블로그에도 독자가 들어올 통로를 마련하려고 시작했다. 네이버의 기존 책 채널과
별도로 영화를 다루며 운영자는 아가톤이다. 예약 저장은 검색 색인이나 유입 성과를 뜻하지 않는다.

글의 중심은 **어떤 사람이 어떤 영화를 보고 무엇이라고 말했는가**다. 영화의 기본 정보·줄거리·
예고편이 감상 배경을 받쳐 주고, 실제 감상 기록이 인물과 작품을 연결한다. 독자는 글 한 편만으로
내용을 이해할 수 있고 인물·작품·목록 링크를 따라 서비스의 다른 기록도 볼 수 있다.

글은 한 영화에 여러 인물의 감상을 모으는 작품 편, 한 사람의 영화 기록을 모으는 인물 편,
영화제·선정 목록 전체와 대표 작품의 감상을 소개하는 목록 편으로 나뉜다.
제작 규격과 자동화 세부 동작은 [채널 문서](../continuous/blog-tistory-cinema.md)가 쥔다.

## 감상문과 제목 정비

앞선 240편에 쓰이거나 교체 후보가 된 감상 **1,271건은 816건 유지·455건 부분 수정**했다.
이번 711편에 새로 쓰인 감상 중 기존 정리 대상 밖의 **1,452건도 1,045건 유지·407건 부분 수정**했다.
두 묶음 모두 루나 맥스가 정리했고, DB의 한영 값·인물/작품 연결·출처 URL을 별도로 재조회해 일치함을 확인했다.

사용자가 정한 것은 **AI SLOP 정리**다. 유용한 영화·플랫폼 해설과 감상 배경은 남기고,
과장·억지 의미 부여·추상적 평론투·반복만 필요한 만큼 부드럽게 덜어낸다. 출처 조사로 넓히지 않는다.
루트는 초반 표본을 조금 더 보고 이후 무작위 표본만 확인했다. 전수 의미 재검수는 하지 않았다.
이전에 출처 감사로 잘못 넓혀 수정했던 18건은 과도한 축약 12건을 복원하고 확인한 오류 6건만 유지했다.

이번 DB 변경은 한영 407건이며, 로컬 한국어 감상문은 신규 인물 226편의 349개 위치에서 바뀌었다.
951편의 본문·제목·태그·미리보기를 다시 만들었다. 감상문 외 재료 차이 0건, 렌더 불일치 0건,
제목 중복 0건이며, 다시 동기화했을 때 갱신할 감상문도 0건이다.
누적 정리 대상은 2,723건이다. 남은 **영화 765건·그 외 영상 562건, 합계 1,327건**은
[기존 별도 TODO](video-review-audit-remainder.md)로 남겼다.

작품 편 헤드라인은 **121/121편 완성**했다. 기존 대부의 「가족을 지키려다 두목이 된 남자」와

`gemini-3.8-flash-high`로 작성했다. 한도에 걸리지 않아 루나 맥스 전환은 필요 없었다.
루트가 표본에서 발견한 추상어·결말 노출·인과 압축은 해당 3편만 같은 모델에 돌려 고쳤다.

각 글 뒤에 붙어 있던 「필앤노트 리뷰」 절은 앞 감상을 되풀이해 로컬 본문 전부에서 걷어 냈다.
그 원문은 `fn-reviews.json`에 보존했으며 이번에도 사용하지 않는다.

## 데이터에서 저장된 글까지

코드는 `sw/web-bo/scripts/tistory-cinema/`, 실제 원고·미리보기·서버 저장 결과는
저장소 밖 **`D:/blog-assets/tistory-cinema/`**에 있다. 코드만 복사해서는 현재 원고와 예약 결과를 복원할 수 없다.

1. `stock.mts`와 `batch.mts`가 DB에서 현재 제작 대상을 계산한다. **별도 대상 원장은 만들지 않는다.**
   인물 ID·slug로 기존 원고를 찾으며 동명이인은 구분한다.
2. 인물 배치는 DB를 한 번 읽고 같은 프로세스에서 재료를 만든다. 기존 원고의 영화 메타와
   `_tmdb-cache`를 재사용한다. 이번에는 부족한 영화 1,103개를 1,103회 TMDB 요청으로 채웠다.
3. 재료 `<이름>.json`을 `render.mts`와 `preview.mts`가 본문·메타·미리보기로 조립한다.
   감상문만 바뀌면 `luna-cinema-refresh-materials.mts`로 관계를 대조하고 기존 구성에 동기화한다.
4. 발행기가 완성된 `_body-*.html`과 `_meta-*.json`을 매 실행 찾고 실제 저장된 이름을 제외한다.
   예정 대상과 날짜는 메모리에서 계산한다. 옛 `_order.json`과 `_schedule-plan.json`을 실행 원장으로 쓰지 않는다.
5. 전용 Puppeteer Chrome이 한 글씩 입력·저장한다. 같은 서버 ID의 편집기를 다시 열어 제목·본문·
   태그·주소·분류·공개 상태·예약일·대표이미지를 대조한 뒤 **성공한 결과만 `_posts.json`에 기록**한다.

대표이미지 첨부·검증은 최초 발행기에 빠져 있어 사용자가 누락을 지적한 뒤 추가했다.
기존 59편 모두 같은 글의 대표사진만 보완했다. 대부·박찬욱·AFI 목록을 화면으로 먼저 확인한 뒤
나머지도 같은 ID로 다시 열어 대표이미지와 본문·제목·태그·주소·분류·공개 상태·예약 보존을 검증했다.
작품 포스터·인물 사진·목록 배너를 기존 재료에서 선택하며,
951편 모두 원본 이미지 주소가 있다. 새 발행기는 대표이미지가 저장되지 않으면 성공 처리하지 않는다.
실제 신규 글의 대표 첨부는 작성 한도 해제 후 첫 발행에서 확인한다. 현재 검증한 실제 저장은 기존 글 수정이다.

사용자가 네이버의 직군·기관별 계층에 영화 장르를 더하도록 지시해, 기존 상위 3개 아래
직군 12개·장르 18개·기관 유형 8개를 만들었다. 인물 26편·작품 29편·목록 4편 모두 하위로 옮겼고,
블로그 사이드바에서도 계층과 글 수를 확인했다. 목록의 카테고리 일괄 변경을 이용해 캡차 입력은 없었다.
59편의 제목·주소·공개/예약 표시·날짜를 재조회했으며 `_posts.json`의 분류 외 필드는 변경 전과 같다.
로컬 951편에는 분류 메타만 추가했다. 본문 SHA-256과 분류 외 기존 메타는 모두 같고,
신규 발행기도 이 메타로 하위 분류를 선택·검증하므로 남은 892편에 같은 기준이 적용된다.
반복 실행은 `sync-categories.mjs --run`이며 이미 맞는 글은 다시 변경하지 않는다.
구성과 입력 규칙은 [채널 문서](../continuous/blog-tistory-cinema.md#세-가지-글)와 `lib/categories.mjs`가 쥔다.

원고 생성 중 끊기면 완성된 인물 원고를 건너뛰고, 발행 중 끊기면 실제 저장된 글을 건너뛴다.
비공개 글에 보존한 옛 `at`은 실제 예약으로 세지 않는다. 복원 시 새 시작일부터 빈 날짜를 계산해
최신 원고와 예약을 한 번에 저장한다. DB 테이블·컬럼이나 별도 진행 대장은 추가하지 않았다.

기존 54편 복원을 메모리에 반영해 신규 897편을 편성한 결과, 전체 951편은
2026-09-09 09:00부터 2027-07-22 18:00까지 들어갔다. 이름·시간 중복은 0건이다.
이는 실행 시 계산한 편성안이며, 아직 저장하지 않은 글까지 예약됐다는 뜻은 아니다.

## 서버 정비와 예약 진행

이전 작업 문서에는 과거 50개 한도 기록이 있다. 9월 6일에는 240편 중 54편이 예약됐고,
신규 예약은 이미 「하루 최대 5개」 알림에 막혔다. 이후 감상문 문제로
9월 7일 추적 중인 54편을 모두 비공개로 내리고 예약을 해제했다. 대장의 옛 날짜는 보존했지만
서버에는 「필앤노트 리뷰」와 옛 제목이 남아 있었다. 과거의 9월 7~24일 편성은 현재 예약이 아니다.

당시 정비한 문제는 태그 미저장, 아카데미 목록의 옛 제목·대표작 순서, 류승완 #53·#55 중복,
같은 시각의 예약 충돌, 본문 강조 표시, 서버 ID·공개 주소·저장 확인 누락이다.
#53을 유지하고 중복 #55는 먼저 비공개로 보존했다가, 9월 8일 사용자의 삭제 지시로 원본을 백업한 뒤 삭제했다.
두 글은 같은 인물·같은 영화 6편의 중복이었다. 삭제 후 검색 화면을 새로 읽어 #53 한 편과 9월 25일 12:00 예약을 확인했다.

9월 8일 재개 때 관리 목록 55편 중 추적 글 54편이 모두 비공개이고 공개 주소도 닫힌 것을 확인했다.
로그인이 만료돼 정상 카카오 로그인 경로로 다시 접속했다. **기존 54편 전부를 최신 본문·제목·태그와
9월 9일 09:00~9월 26일 18:00 예약으로 복원했다.** 각 글을 저장 후 다시 열어 대조했고
추적 글의 비공개 0편·예약시간 중복 0건을 확인했다. 별도 중복 글 #55는 이후 사용자 지시로 삭제했다.
신규 897편 중 산딸기 #56, 다니엘 데이루이스 #57, 타임아웃 100대 공포영화 #58을
9월 27일 09:00·12:00·18:00에 각각 저장하고 같은 ID로 재조회했다. 이 단계에서 확정 예약은 57편이었다.

다음 신규 글 스카페이스의 작성 화면을 열기 전, 관리 목록 page 4 조회에서 30초 대기 후
티스토리 오류 화면으로 이동했다. 화면에는 **“과도한 접근 요청으로 블로그 사용이 잠시 중단되었습니다.
자동화된 접근 등을 시도할 경우 서비스를 이용하실 수 없습니다.”**라고 표시됐다.
스카페이스 저장 요청은 하지 않았고 신규 배치는 성공 3편만 기록한 뒤 exit 1로 종료했다.
당시 중단 원인은 이 접근 제한이며 해당 실행에서 일일 작성 한도 알림은 관측하지 않았다.
남은 원고는 894편이었다. 추가 요청·우회·자동 재시도를 멈췄고, 사용자 재개 지시 후 정상 관리 화면을 확인했다.
이 실행의 복원·발행 Node 프로세스와 캡차 감시는 종료됐고 브라우저 잠금 파일도 정리됐다.

접근 복구 후 전체 관리 목록을 글마다 반복하지 않고 배치 시작에 한 번만 읽도록 고쳤다.
저장 뒤 실제 ID를 찾아 다시 열어 대조하는 검증은 유지했다. 관련 38개 시험을 통과한 뒤
스카페이스 #59를 9월 28일 09:00, 클린트 이스트우드 #60을 같은 날 12:00에 저장·재조회했다.
칸 황금종려상은 인증 제출 직후 하루 최대 5개 알림으로 저장되지 않았으며 배치는 성공 2편만
기록하고 종료했다. 오늘 신규 작성은 앞선 3편을 합쳐 5편이다. 현재 59편 모두 예약 상태이며
실제 ID·원고 이름·예약 시각 중복은 없다. 사용자는 중복 조회와 보고를 줄이고 한 작업자가
발행·캡차를 맡아 관리하도록 지시했다. 루트는 같은 화면을 반복 열지 않고 결과와 오류만 확인한다.

처음 저장은 과거 발행일이 선택돼 있어 예약 버튼이 반응하지 않았다. 실제 화면에서
현재→예약 순서로 바꾸면 날짜 입력이 열리는 것을 확인해 코드와 회귀시험에 반영했다.
그다음 캡차 서비스가 `Bad Request`를 반환해 실패했으나 새 시도에서는 정상 문제가 나왔고,
답을 입력해 #1 대부의 새 원고와 9월 9일 09:00 예약 저장·재조회를 완료했다. 이후 21편째까지
성공한 뒤 같은 서비스 오류가 한 차례 더 나왔지만 새 요청에서 회복돼 나머지 33편도 모두 저장했다.

캡차는 사용자가 승인한 대로 현재 화면을 읽고 정상 답 입력으로 처리한다. 문제가 없는 서비스 오류를
무기한 기다리지 않도록 오류 감지와 종료 처리를 보완했다. 확대 상태에서 문제가 잘리던 캡처도
현재 화면 전체를 저장하도록 고쳤다. 세부 입력 방법은 [채널 문서](../continuous/blog-tistory-cinema.md#캡차와-저장-실패)를 따른다.

## 이어서 실행할 명령

실행 위치는 `sw/web-bo`다. 신규 작성이 다시 허용되면 아래 명령으로 남은 892편부터 이어간다.
발행기가 현재 원고와 `_posts.json`으로 빈 미래 일정을 계산하고, 실행 시작에 서버 전체 목록을
한 번 확인한다. 현재 기록 기준 첫 글은 칸 황금종려상이며 이미 저장한 59편은 자동으로 제외된다.
한 작업자가 배치와 정상 캡차를 맡고, 루트는 중복 화면 조회 없이 결과와 오류를 확인한다.

```bash
# 남은 원고 편성 미리보기 / 실제 저장·검증
node scripts/tistory-cinema/agent-publish.mjs --plan --days 366 --limit 951
node scripts/tistory-cinema/agent-publish.mjs --run --days 366 --limit 951
```

실행 도구가 편성·저장·검증을 이어가고 에이전트에는 새 캡차·입력 오류·최종 결과만 전달한다.
Codex에서는 `tty:true`로 실행해 같은 세션의 stdin으로 답한다. 매번 로그를 다시 읽지 않는다.
입력 형식과 파일 입력 대안은 [채널 문서](../continuous/blog-tistory-cinema.md#캡차와-저장-실패)에 있다.
이 도구는 모의 발행·터미널 답 전달·실제 892편 미리보기를 검증했다. `_posts.json` 해시도 같았다.
새 도구를 통한 실제 발행은 아직 하지 않았다. 다음 재개 때 첫 저장 결과를 확인하고 이어간다.

한도나 저장 오류가 나오면 전체 배치가 멈춘다. 그 전에 저장·검증한 글은 기록되어 다음 실행에서
제외된다. 9월 8일 신규 5편 저장 뒤 「하루 최대 5개」 알림을 실제로 확인했다. 한도 숫자를 발행기의
고정 상수로 두지는 않으며, 다음 실행에서도 플랫폼의 실제 알림을 따른다. 날짜가 바뀌면
이전의 50개 한도로 돌아온다고 가정하지 않는다. 한도 축소에 관한 공식 안내는
[채널 문서](../continuous/blog-tistory-cinema.md#발행-한도-알림을-만나면-전체-실행을-멈춘다)에 연결했다.
자정 감시나 자동 반복 발행은 걸지 않는다. 전용 Chrome은 포트 9333, 프로필 `C:/project/_chrome-tistory`다.
